# Worker processing pipeline performance audit

Scope: static read-only review of the v3 Worker path from startup and material confirmation through model analysis, rendering, encoding, output validation, and report delivery. No code or legacy assets were changed. `fast_context_search` is not available in this tool session, so findings were traced with targeted `rg` searches and line-numbered reads.

## Existing sample evidence

The sibling audit extracted these stage totals from the existing 5-source smoke run (27 outputs, three render workers, zero incremental output reuse): decode 1.430 s, analysis 2.631 s, compose 42.405 s, overlay 0.783 s, encode 27.363 s, write 0.677 s, and 75.291 s across reported stages. These are accumulated stage/job durations, not end-to-end wall time; work across the three render jobs can overlap. This audit did not rerun or benchmark the sample. The evidence makes compose and encode the first rendering targets; it does not establish time spent in the earlier confirmation/model stage.

## Actual execution path and concurrency

- A `ping` also returns `ready` with the same payload; it does not run a model probe (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/worker.py:537-545`). Main/settings WebViews send pings on mount, and Tauri broadcasts worker lines to WebViews (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/apps/desktop/src/App.vue:1237-1241`; `/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/apps/desktop/src-tauri/src/main.rs:678-692`). Each eligible WebView can therefore call `probe_models` for the same `ready` event (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/apps/desktop/src/App.vue:1427`). This is a duplicate-probe path, conditional on models being configured and enabled.
- `classify_materials` runs on one Worker background thread (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/worker.py:356`). It collects files once and shares them with preflight and the classifier (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/worker.py:472`). Rule classification receives the UI-selected count; the app caps it at four (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/apps/desktop/src/App.vue:1636-1649`), and the bundled rule classifier uses a pool only for four or more sources (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/legacy_engine/category_engine/source_type_classifier.py:267-291`).
- Optional model work is serial by source. Preserve this lock unless model-session safety, cache races, CPU oversubscription, and memory multiplication are measured and addressed; adding model workers is not the first measured render optimization.

## Highest-value rendering opportunities

1. **Reuse the same composed canvas for logo/no-logo outputs.** With `include_logo`, the engine creates two requests per selected size; this flag does not affect `_compose` (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/engine.py:423`; `/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/renderer.py:675`). Both requests therefore repeat the same base composition before applying separate overlays. This is the clearest candidate against the measured 42.405 s compose total (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/renderer.py:1124`). VIP may share a canvas only when every compose-affecting argument matches: the regular main request passes `background` and sets layout `scale` and `allow_mirror_extension` (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/engine.py:435`), while the VIP request omits those fields in its builder/layout arguments (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/engine.py:501`). Keep any reuse short-lived and immutable; copy before overlays, and compare output parity and peak memory before changing concurrency.

2. **Build a transparent cutout once per PNG source when no category template applies.** Whenever any output size is selected, every PNG source is queued for four transparent sizes (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/engine.py:546`). On the transparent path, a category template returns before alpha extraction; without a template, a light-background input calls `_background_to_alpha` on the full source (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/renderer.py:709`). That function materializes all pixels and executes a Python loop for every pixel (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/renderer.py:543`). Thus up to four full-source alpha passes are possible per PNG, but whether this affected the knee-pad smoke sample depends on its category-template setting, which the sample did not record. If applicable, cache the exact cutout/crop for the source batch and resize per target; preserve the pixel rule and compare output pixels.

3. **Make PNG quantization candidates lazy; count encoder attempts before changing quality settings.** When a PNG size cap is set, `_encode_png` eagerly creates 256/128/64/32-color quantized images before encoding the original RGBA image (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/renderer.py:570`). The encoder then checks candidates in that same order and returns at the first candidate under the limit (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/renderer.py:581`). Generate each quantized candidate only after the preceding candidate misses the size limit; this preserves candidate order and selected output while avoiding quantization work for unused candidates. JPEG output uses `optimize=True`; with `max_size_mb`, it re-encodes at decreasing quality in steps of five until under the limit or quality 45 (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/renderer.py:554`). VIP also JPEG-encodes a temporary image before border compositing, then the normal output path encodes again (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/renderer.py:829`, `/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/renderer.py:925`); the source comment says this preserves legacy output behavior. With 27.363 s measured encode time, laziness is a low-risk concrete optimization; check whether the sample had a size cap and count JPEG attempts before changing compression/quality or the VIP intermediate, which may change output compatibility.

## Secondary findings and limits

- Pose/Seg disk results are keyed with an exact SHA-256 of each source. A single classification request caches that digest per source and shares it among Pose/Seg lookups (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/classification.py:448`); each new classification request reads each eligible source fully to build that digest. Cache identity also includes model versions, purpose, category, composition rules, and a seven-day TTL (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/model_cache.py:21`, `/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/model_cache.py:82`). Keep the identity semantics; profile source hashing before considering a digest cache, since a stat-keyed digest cache trades exactness if a file is changed while preserving size and mtime.
- Repeated model probes reuse assistant sessions keyed by model path and stat version (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/model_service.py:77`), but each probe still computes a full SHA-256 for every configured model (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/model_service.py:200`, `/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/model_service.py:422`). The duplicate WebView-triggered probes can repeat model-file reads and queue behind inference. A small single-flight/ready-state guard at the app boundary is lower risk than loosening the model lock.
- Generation receives confirmed source types and metadata, so the normal UI path avoids a second V3 classification pass (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/engine.py:283-305`; `/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/apps/desktop/src/App.vue:1094-1115`). It still enumerates the input tree again for generation (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/engine.py:278`); likely low value compared with rendering unless folders are very large.
- Existing output reuse checks only whether the expected path exists unless `force_rerender` is set (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/engine.py:470`, `/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/engine.py:528`, `/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/engine.py:576`). It can save substantial work on repeat runs, but there is no source/settings fingerprint in that gate. Do not expand reuse until correctness invalidation is addressed.
- Render stage timings are surfaced in `performance`; output validation then reopens each generated file and checks header/size (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/engine.py:730`; `/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/renderer.py:916`, `/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/renderer.py:1203`). This post-render work is not represented in the listed compose/encode totals. It is a lower-priority wall-time candidate unless a real wall-clock sample shows validation is material.
- `_worker_build_hash()` reads all of `sys.executable` when frozen on each Worker process start (`/Users/weiheng/Desktop/PixelFlow/PixelFlow-App-v3-beta/worker/pixelflow_core/worker.py:32`). A ping reuses the value and does not hash again. This may add cold-start I/O, but the existing render sample says nothing about launch latency; only pursue if startup timing identifies it.

## Minimal priority order

1. Prototype in-batch reuse for logo/no-logo outputs; consider VIP only when every compose-affecting argument matches. Validate parity and peak memory.
2. If the sample includes light-background PNGs, cache one alpha extraction/crop per source; validate pixel parity and transparent outputs.
3. Lazily create PNG quantized candidates in the existing order, and count encoder attempts; retain the VIP compatibility step unless a baseline-approved alternative is demonstrated.
4. Separately guard duplicate `probe_models` calls across ready/ping events. Keep model requests serial until safe model-session concurrency and memory costs have evidence.

No acceleration percentages are inferred from the accumulated stage timings.
