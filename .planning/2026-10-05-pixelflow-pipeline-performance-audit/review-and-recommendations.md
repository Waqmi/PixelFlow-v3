# PixelFlow v3 性能审核复核与建议（2026-10-05）

代码基线 a6a6131，未修改产品代码。对象：同目录 `performance-review.md`（及 `worker-pipeline.md`、`measurements.md`、`ui-host.md`）。实测脚本与原始输出在 `bench/`、`bench/results/`。

## 1. 结论

- 原审核方法严谨（不把累计计时当墙钟、不盲目加并发、保留模型锁），列出的问题都真实存在；但**漏掉了最大的瓶颈，且第一批的优先级排错了**。
- 最大瓶颈是 `_background_to_alpha` 的纯 Python 逐像素循环（[renderer.py:543](../../worker/pixelflow_core/renderer.py)）：一张 4.2MP 图每次 3.1s，每个 PNG 来源跑 4 次，并且持有 GIL，使 3 个渲染线程基本串行（产品批量原版 2→3 线程只快 4%；模特批量没有这段循环，3 线程快 2.6×）。
- 第二大瓶颈是 PNG 编码对每个候选都做 `compress_level=9 + optimize`，而不是原审核说的“提前量化 4 份”（量化每份仅 0.02–0.03s）。
- 在冒烟同形态负载（护膝 5 来源 → 27 输出）上，3 线程墙钟：仅 numpy 抠图（逐字节一致）**31.9s → 11.2s**；再加宽松 PNG 分级（像素一致）**→ 5.8s**。v3 渲染端仍有明显优化空间，首选是 numpy 向量化抠图。
- 原审核第一批第 2 项“Logo/无Logo 共享构图”：对产品图收益很小（单次 0.03–0.07s），但对 side fill 模特图有效（单次 0.45–0.88s，模特批量里 compose 占 82% 墙钟）。应改为按来源类型评估，排在前两项之后。

## 2. 对原审核的评价

认可：

- 累计阶段计时不是墙钟、不能算吞吐（`measurements.md`）。实测进一步证明：原版 3 线程时 compose 累计 41.97s，单线程只有 24.35s——多出来的是 GIL 排队时间，冒烟报告的 42.4s 正是这种虚高。
- 不直接把并发调到核数、不放开模型锁、不降 JPEG 质量、VIP 中间 JPEG 保留。
- PNG 候选惰性生成方向正确（但收益来源判断错，见下）。
- 多窗口重复 probe、确认页 Map/Set 索引：本次未测，维持原审核的低优先级判断。

需修正：

| 原审核条目 | 原判断 | 实测 / 修正 |
|---|---|---|
| 第二批 #4 透明图只做一次抠图 | 中后优先级，用缓存解决 | **应升为第一优先级**。改用 numpy 向量化（25×，逐字节一致）比缓存（最多省 3/4）更有效；向量化后缓存收益可忽略 |
| 第一批 #1 PNG 候选按需生成 | 浪费在 4 次量化 | 量化 4 份合计约 0.1s；真实成本是对注定超限的候选做 L9+optimize（1440 以上尺寸原图 L9 都超 0.9MB，每次 0.7–2.0s） |
| 第一批 #2 Logo/无Logo 共享底图 | 中等风险、优先验证 | 两份 compose 确实逐字节相同（产品图 VIP 与无Logo 也相同）。产品图单次 0.03–0.07s，收益小；side fill 模特 0.45–0.88s，模特批量可省约 3/7 compose。排第 3 |
| 第二批 #6 JPEG 多轮编码 | 需计数 | 已计数：所有尺寸 q95 一次达标，单张 0.02–0.04s，不是瓶颈 |
| 并发 | 1/2/3 留到后面测 | 已测：原版 2→3 线程仅快 4%；去掉 Python 循环后 3 线程比 1 线程快 2.0–2.4× |

## 3. 实测数据

环境：macOS 15.7.7 arm64，10 核，Python 3.14.5，Pillow 12.3.0，numpy 2.5.3（worker/.venv）。每项取 3 次中位数。

素材：`~/Desktop/PixelFlow/05_测试素材与输出/护膝/` 3 张 PNG（1536×2752、1152×1536、1792×2400，其中两张浅底）+ 2 张 WebP；`热能长裤/` 模特 JPEG 4943×7415。大小上限 0.9MB。

### 3.1 端到端墙钟（`V3EngineAdapter.run`，护膝 5 来源 → 27 输出，含 Logo + VIP + 4 透明尺寸）

| 方案 | 1 线程 | 2 线程 | 3 线程 | 3 线程 CPU/墙钟 | 输出逐字节一致 |
|---|---:|---:|---:|---:|---|
| 原版 | 49.02s | 33.25s | 31.93s | 1.54 | — |
| numpy 抠图 | 26.94s | 16.86s | 11.16s | 2.40 | 是 |
| numpy 抠图 + PNG 分级（L6 达标即出） | 11.42s | 6.62s | 5.84s | 1.92 | 否，仅像素一致（见 3.3） |

每次冷解码（清 `_source_image` 缓存），`force_rerender`，0 失败。

### 3.2 抠图（H1）

| 源图 | MP | 原版 | numpy | 加速 | 逐字节一致 |
|---|---:|---:|---:|---:|---|
| 1536×2752 | 4.23 | 3.188s | 0.125s | 25× | 是 |
| 1152×1536 | 1.77 | 1.272s | 0.050s | 26× | 是 |
| 1792×2400 | 4.30 | 3.106s | 0.126s | 25× | 是 |

透明路径 compose 单次：浅底大图 3.15–3.24s → 0.17–0.22s；非浅底图（不走抠图）0.01–0.04s 不变。

### 3.3 PNG 编码（H2，12 张透明画布，上限 0.9MB）

| 方案 | 12 张合计 | 与原版关系 |
|---|---:|---|
| 原版 `_encode_png` | 22.5s | — |
| 精确分级：L6 试探明显超限（>10%）的候选跳过 L9，其余同原版 | 12.3s | **逐字节一致**（12/12） |
| 宽松分级：L6 达标直接输出 | 6.9s | 解码后像素一致（12/12），文件字节不同 |

原版每个候选 L9 耗时 0.1–2.0s，量化本身 0.007–0.032s。1440×1440 及以上尺寸原图 L9 均为 1.2–4.0MB，必然超限。

两种分级在 12 张图上都选中与原版相同的候选（raw / q256 / q64），所以像素不变。宽松方案输出的是 L6 码流，文件大小为原版的 -14%～+4%（量化候选的 L6 码流反而常比 L9+optimize 小），都在 0.9MB 以内。

两种方案都依赖一个经验前提：L9+optimize 比 L6 最多小 10%（本次实测为 0.1–4%）。若某候选 L6 超限 10% 以上而 L9 恰好达标，会被跳过，改选后一个更低色数的候选。落地时保留余量参数，并在更大语料上统计 L9/L6 比值。

### 3.4 构图与 JPEG（H3/H4，单次）

|---|---:|---:|---|
| 产品图（浅底 PNG / WebP） | 0.03–0.07s | 0.01–0.015s | 0.02–0.04s（1 次，q95） |

### 3.5 模特批量（Batch B：热能长裤 3 张 4943×7415，side fill，3 尺寸 + Logo + VIP → 21 输出，原版）

| 线程 | 墙钟 | CPU/墙钟 | 累计 compose | 累计 encode |
|---:|---:|---:|---:|---:|
| 1 | 17.27s | 1.00 | 14.23s | 0.56s |

### 局限

- 只有护膝一组产品素材和热能长裤 3 张模特图；批量 B 用人工构造的越界 crop_box 触发 side fill，非真实 Pose 计划。
- 未测启动、Pose/Seg 推理、确认页 UI、报告渲染、多窗口 probe、峰值内存。
- 宽松 PNG 分级的“选中候选”行为只在 12 张图上验证，需在更大语料上确认。

## 4. 优化建议（按收益/风险排序）

1. **`_background_to_alpha` 改为 numpy**（收益最大，风险低，逐字节一致）。原型见 `bench/common.py:background_to_alpha_numpy`：int16 求通道差最大值，float64 计算 `(d-8)*255/40`，`np.rint`（与 Python `round` 同为 half-to-even），`np.where` 套 0/255 阈值。验证：新增单测对随机图 + 边界值 d∈{8,9,47,48} 及 .5 舍入点与旧实现逐字节比较；跑 `worker/tests` 全量与 `tools/verify_output_baseline.py`。
2. **PNG 精确分级编码**（收益大，风险低，逐字节一致）。原型 `bench/common.py:encode_png_gated_exact`：每个候选先 L6 编码，若超限 10% 以上则跳过其 L9；量化候选惰性生成；全部未达标时补做被跳过候选的 L9，保持“返回最小 L9”的原语义。依据：L9 相对 L6 只小 0.1–4%，10% 余量安全。验证：同上，再加一组“全部候选都超限”的用例。
3. **（需产品决定）PNG 宽松分级**：L6 达标直接写出。在 1、2 基础上再省一部分（1+宽松 的 3 线程墙钟 5.8s；1+精确 未单独跑批量，按编码合计 12.3s vs 6.9s 估计介于 5.8s 与 11.2s 之间）。像素不变，文件字节和大小变化（仍在上限内）。若接受，需同步更新基线比对口径为“解码后像素一致”。
4. **同来源同尺寸含/无 Logo 共享 compose 结果**（模特 side fill 批量收益明显，逐字节一致）。在 `render_source_batch` 内按“影响 compose 的全部参数”做键缓存，叠加前 `copy()`；VIP 只在键完全一致时复用（模特 VIP 本次未验证）。按 Batch B 估算单线程累计 compose 14.2s → 约 8s；需测峰值内存（每个 1440×2160 RGB 底图约 9MB）。
5. **在 1、2 落地后重测并发**：目前 `render_workers = min(3, len(sources))`（[engine.py:322](../../worker/pixelflow_core/engine.py)）。numpy 版 3 线程 CPU/墙钟 2.40，可能还有空间，测 3/4 线程与峰值内存后再定，不直接设为核数。
6. **补墙钟计时**（原审核“怎样证明”一节，认同）：engine 结果里加 batch 墙钟和 spawn→ready、done→报告可见；当前报告的 `total_seconds` 是累计值，容易误读。
7. 低优先级、本次未测，维持原审核：多窗口 probe 单飞、确认页 Map/Set 与 rAF 合并。

## 5. 暂不建议

- **直接把渲染并发调到核数**：原版下无效（GIL），numpy 版下需先测内存。
- **放开模型锁 / 并行 ONNX**：无测量，且有会话安全与内存风险。
- **降低 JPEG 质量或移除 VIP 中间 JPEG**：JPEG 不是瓶颈，且影响兼容性。
- **缓存透明抠图结果**：numpy 后单次 0.125s，缓存省不了多少，反而增加内存。

## 6. 验收方法

- 复用 `bench/bench_batch.py`（护膝 27 输出）与 `bench/bench_png_exact.py`，改动前后同机对比，取 3 次中位数。
- 1、2 的验收标准：输出文件逐字节一致（可对 `force_rerender` 前后输出目录做 sha256 比对）；单测全绿；`tools/verify_output_baseline.py` 通过。
- 3 的验收标准：解码后像素一致、文件 ≤ 上限，并在 100% 缩放下抽查透明图。
- 本次单测基线：`PYTHONPATH=worker worker/.venv/bin/python -m unittest discover -s worker/tests -p 'test_*.py'` → 193 通过，1 skip。

## 7. 实施记录（2026-10-05）

已改 `worker/pixelflow_core/renderer.py`：建议 1（numpy 抠图）与建议 2（PNG 精确分级）。探测余量取 `PNG_PROBE_MARGIN = 0.20`：在 60 张抽样源图、244 张透明画布、1220 个候选上，L6/L9 最大 1.113（p99 1.081）。余量 0.10/0.20/0.35/0.50 的输出都与 HEAD 逐字节一致（0/240），0.20 留出余地且几乎不慢（语料编码 370s → 211s）。合成的“渐变 + 噪声”图可使 L6/L9 > 1.2，因此余量是经验值而非保证。数据见 `bench/results/bench_png_margin.txt`。
