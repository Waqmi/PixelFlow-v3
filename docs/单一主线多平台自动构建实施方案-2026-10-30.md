# 单一主线多平台自动构建实施方案

日期：2026-10-30  
适用项目：PixelFlow v3

## 1. 目标

将项目整理为“单一主线源码，多平台自动构建”的发布流程：

- `main` 是唯一长期维护的代码主线。
- macOS ARM64、macOS Intel x86_64、Windows x64 从同一个 commit 构建。
- Intel 和 Windows 临时分支只作为差异来源和历史备份，不再作为长期代码来源。
- `.app`、`.exe`、`.zip` 等构建产物不提交回源码分支。
- 普通 `main` 更新用于测试和构建验证；版本 tag 用于生成正式 Release。

### 2.3 源码修改分类

Windows 分支中的修改需要按以下方式处理：

#### 应合入 `main` 的通用修改

- Worker 引擎、分类、渲染和缓存逻辑。
- 重复输出、文件名冲突和失败回退处理。
- 前端任务状态、进度和结果显示。
- 与上述逻辑对应的测试。

#### 保留为平台判断或平台配置的修改

- Windows 文件选择器、路径和编码处理。
- Windows Worker 启动、无控制台窗口和进程管理。
- Windows 图标和 Tauri 打包参数。
- Windows 专用 GitHub Actions 步骤。

这些逻辑应继续通过 `#[cfg(target_os = "windows")]` 或平台构建配置隔离。

#### 不进入源码分支的构建产物

- `downloads/PixelFlow_3.0.0_x64-portable.exe`
- 已编译的 `.app`、`.exe`、`.dmg`、`.zip`
- `dist/`、`build/`、Tauri `target/` 和 PyInstaller 输出目录

图标等构建输入资源可以保留；安装包和可执行文件必须改为 Actions artifact 或 Release asset。

## 3. 实施方案

### 阶段一：建立集成工作树

1. 从当前 `main` 创建独立集成分支或 worktree。
2. 保留所有现有临时分支，不删除、不重写历史。
3. 记录 `main`、Windows 分支和 Intel 源码副本的提交、状态和差异摘要。
4. 明确未跟踪规划文件不参与源码合并。

验收：集成工作树干净，现有分支仍可独立检出，差异来源可追溯。

### 阶段二：整理通用源码

1. 从 Windows 分支选择性移植通用 Worker、UI 和测试修改。
2. 手工处理 `apps/desktop/src-tauri/src/main.rs`、`apps/desktop/src/App.vue` 和 Worker 核心文件中的重叠修改。
3. 保留 Windows 专用平台判断和构建配置。
4. 评估 Intel 的输出完整性修复，确认通过 ARM 行为测试后再合入 `main`。
5. 不将 EXE、APP、ZIP 或其他编译目录加入 Git。

验收：`main` 包含需要的通用行为；Windows 专用代码仍有明确平台边界；ARM 现有功能不被覆盖。

### 阶段三：统一 CI 触发方式

将 CI 分成两层：

#### `main` push 和 Pull Request

运行测试和构建验证：

- Worker 单元测试。
- 协议检查。
- 前端生产构建。
- Tauri host 编译检查。
- 可用平台上的实际打包验证。

每个平台使用 GitHub Actions 的 `${{ github.sha }}` 作为源码提交标识，并在日志和 artifact 元数据中输出。

#### 版本 tag

例如推送 `v3.0.1` 时：

- 三个平台都从该 tag 对应的同一个 commit 构建。
- 生成带平台和架构名称的安装包。
- 上传到 GitHub Release。
- 不向 `main` 或任何平台分支提交安装包。

推荐的产物名称：

```text
PixelFlow-v3.0.1-macos-arm64
PixelFlow-v3.0.1-macos-x64
PixelFlow-v3.0.1-windows-x64
```

### 阶段四：配置三个平台构建

#### macOS ARM64

- 使用可用的 Apple Silicon runner。
- 构建 Worker 和 Tauri `.app`，必要时生成 `.dmg`。
- 校验主程序和 Worker 为 `arm64`。

#### macOS Intel x86_64

- 优先使用可用的 Intel macOS runner 或 self-hosted Intel Mac。
- 使用 x86_64 Python、依赖、PyInstaller 和 Tauri target。
- 校验主程序、Worker 和内置动态库为 `x86_64`。
- 在 Intel Big Sur 或目标最低系统上完成启动、设置保存、退出和输出回归。

当前 `macos-14` 是 Apple Silicon runner，不能替代 Intel 构建验证。若 GitHub 账号没有 Intel runner，需要配置 self-hosted Intel Mac，并把 runner label 固定在 workflow 中。

#### Windows x64

- 使用 `windows-2022` runner。
- 保留现有 NSIS 和 portable EXE 构建步骤。
- 移除提交 `downloads/` 回分支的步骤。
- 上传 NSIS、portable EXE 和构建元数据为 artifact 或 Release asset。
- 继续运行 Worker ready/ping、进程存活和中文路径等 Windows 检查。

## 4. 产物和发布规则

### 普通 main 构建

产物上传为 Actions artifact，名称至少包含：

- 平台。
- 架构。
- commit SHA。

例如：

```text
pixelflow-main-macos-arm64-<sha>
pixelflow-main-macos-x64-<sha>
pixelflow-main-windows-x64-<sha>
```

### 正式版本构建

只有版本 tag 触发正式 Release 上传。Release 中应包含：

- 三个平台安装包。
- SHA-256 校验文件。
- 构建 commit SHA。
- 平台和架构说明。
- 签名、公证和代码签名状态。

构建失败时，workflow 必须让对应平台 job 失败，并在 Actions 页面显示失败平台和失败步骤。Release 不应在三个平台没有全部成功时标记为完整发布。

## 5. 风险和冲突点

### 已确认风险

- Windows 分支包含大量历史打包提交，不能直接整分支合并。
- Windows workflow 当前会向分支提交二进制，需要先删除该行为。
- Intel 没有长期 Git 分支，也没有可复用的 GitHub-hosted Intel runner 证据。
- 当前机器不能完成 Windows 实机打包和 Intel Big Sur 真机验收。
- Intel Python、ONNX Runtime、PyInstaller 和 Tauri 依赖必须确认能生成 x86_64 版本。
- 当前没有 Developer ID、公证或 Windows 代码签名配置，首版 Release 可能是未签名或 ad-hoc 签名。

### 需要人工确认

- 是否承诺继续支持 Intel macOS，以及最低 macOS 版本。
- 是否有可用的 Intel Mac self-hosted runner。
- 是否有 GitHub Actions 足够的 macOS/Windows 构建额度。
- 是否现在就配置签名、公证和 Windows 代码签名。
- 正式版本号和 Release 命名规则。

## 6. 验收标准

- `main` 更新后，测试和三个平台构建任务按配置触发。
- ARM、Intel、Windows job 使用同一个 commit SHA。
- ARM 产物包含 `arm64` 主程序和 Worker。
- Intel 产物包含 `x86_64` 主程序和 Worker。
- Windows 产物为 x64，并通过 Worker 和应用启动检查。
- 构建产物可以从 Actions artifact 下载。
- 版本 tag 对应的三个安装包可以从 GitHub Release 下载。
- 安装包没有被自动提交到 `main` 或平台临时分支。
- 现有 Worker、前端和 Rust 测试通过。
- Intel Big Sur 和 Windows 实机限制被明确记录，不把静态检查写成实机验证。
