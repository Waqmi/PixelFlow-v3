### T4（P1）预览性能与 `read_file_bytes` 安全修复

**问题**

- `App.vue:1162` 用 `invoke<number[]>('read_file_bytes')` 读取**原图全部字节**。Tauri 会把 `Vec<u8>` 序列化成 JSON 数字数组，一张 5 MB 的 JPG 会变成十几 MB 的 JSON，素材一多界面就会明显卡顿。这也正是 CONF-05（异步缩略图，不阻塞界面）一直没有通过的根源。
- `read_file_bytes(path)` 能读取任意路径，WebView 一旦被注入脚本，就可以读取用户的任意文件。同时 `tauri.conf.json` 中 `csp: null`，也就是没有设置内容安全策略。

**步骤**

1. 由 Worker 生成缩略图：新增协议消息 `make_thumbnails`，输出最长边 256–320 px 的 JPEG，缓存在应用缓存目录，以源文件 SHA-256 或 mtime+size 作为键。
2. Host 端二选一：
   - 用 `tauri::ipc::Response::new(bytes)` 返回二进制，避免 JSON 数组；
   - 或者启用 asset protocol，把 scope 限定在缩略图缓存目录，前端用 `convertFileSrc`。
3. 限制 `read_file_bytes`（如果还保留）只能读取当前任务的输入目录和缩略图缓存目录，越界直接拒绝。
4. 设置最小 CSP，例如 `default-src 'self'; img-src 'self' asset: http://asset.localhost blob: data:`。
5. 前端对缩略图做懒加载（IntersectionObserver），并限制同时进行的请求数。

**验收**：300 张素材进入确认页时，首屏在 1 秒内可以交互，滚动不卡顿；越界路径请求���回错误；CONF-05 标记为 ✅。

### T7（P1）Worker 打包方式与 Python 版本

**现状**：正式 Worker 是 PyInstaller **onefile**（约 32 MB），使用 v2.0 `.venv` 中的 **Python 3.9.13** 构建。

**问题**

- onefile 每次启动都要解压到临时目录，冷启动慢；普通沙箱中出现的 `semctl` 报错也来自 onefile 启动器。
- 签名公证时，onefile 解压出来的 dylib 无法预先签名，公证和 Gatekeeper 容易出问题。
- Python 3.9 已于 2025-10 停止安全更新，而且和 v2 共用 `.venv`，v3 的构建环境无法独立复现。

**步骤**

1. 把 onedir 实验（`frozen-worker-ondir-evidence.json`，已经全部通过）转为正式方案：
   - Tauri `bundle.resources` 改为映射整个 `pixelflow-worker/` 目录；
   - `spawn_worker` 改为查找 `Resources/pixelflow-worker/pixelflow-worker`。
2. 为 v3 建立独立的构建环境，例如 `worker/.venv`，使用 Python 3.12，并用 `worker/requirements.lock` 锁定 Pillow、NumPy、onnxruntime、PyInstaller 的版本。
3. 升级后重跑 83 项测试、T3 的基线比较和鞋类模型证据，确认升级 Python 和依赖没有引入像素变化。如果有变化，写入基线来源说明。
4. 在构建脚本末尾自动生成 `worker-artifact-hashes.json`，避免手工记录。
5. 记录冷启动时间，onefile 和 onedir 对比（从进程启动到收到 `ready`）。

**验收**：`.app` 内置 onedir Worker 通过 T2 回归；构建不再依赖 `PixelFlow-App-v2.0/.venv`；冷启动时间有记录。

### T9（P2）前端结构、测试与 CI

**现状**：`App.vue` 有 1539 行，承担全部页面、状态和协议处理；前端没有任何测试；仓库里没有 CI。

**建议**

1. 拆分 `App.vue`：
   - `views/`：主界面、确认页、结果页、设置页；
   - `composables/`：`useWorker`、`useMaterials`、`useProgress`、`usePreferences`。
2. 协议类型从 `packages/protocol/schema.json` 生成（例如 `json-schema-to-typescript`），避免 `workerProtocol.ts` 和 Python `contracts.py` 各自手写后逐渐不一致。另外增加一个契约测试：Python 端产出的示例消息必须通过 schema 校验。
3. 引入 Vitest，至少覆盖 `workerClient.ts`（请求 ID、超时、错误事件）和进度追赶逻辑。
4. 使用 GitHub Actions：
   - `worker`：`unittest discover`（macOS + Windows）；
   - `desktop`：`npm run build`（vue-tsc）和 `cargo check`；
   - 可选：手动触发的打包工作流，产出 `.app` 和 Windows 安装包。

### T11（P2）定义并执行 legacy 兼容周期

`legacy-compatibility-cycle.json` 目前 `status=active`，但“一个版本周期”没有量化标准。建议补充以下定义：

- 周期至少覆盖一个对外 beta 版本（例如 `3.0.0-beta.2`），并满足时间或批次条件，例如 ≥ 2 周，或 ≥ N 个真实批次；
- 期间 v3 Renderer 的自然回退（排除故障注入）次数为 0，或者每一次都已定位并修复，统计来源见 T8 第 4 项；
- T3 中“需修复”的差异已清零；
- 满足以上条件后，再单独开一项任务评估删除 `legacy_engine`，并同时去掉 `compare` 对 legacy 的依赖，或者把 compare 改为 v3 前后版本对比。

## 3. 其他建议

1. **性能基线**：为 16 张固定素材和 20 张鞋类素材分别记录 v2.6 和 v3 的总耗时、单张耗时、峰值内存。另用约 500 张素材做压力测试，确认不会随批次增大而内存上涨。之后再考虑 Worker 内的多进程渲染。
2. **扩大素材覆盖**：固定素材目前只有暗夜黑长裤和鞋类。建议补充浅色或白色商品（覆盖 v2 的“浅色商品保护”）、上衣/外套、透明或反光材质、超大图（> 6000 px）、CMYK JPG、带 EXIF 旋转的图片、带 alpha 的 PNG、损坏文件和中文长文件名。
3. **诊断包导出**：在设置页提供“导出诊断信息”，把 App 版本、Worker 版本和哈希、规则版本、模型哈希、最近日志和失败报告打成一个 zip，方便远程排查。
4. **关于页 / 版本信息**：显示 `3.0.0-beta.1`、Worker 构建哈希前 8 位、`v3-composition-1`、模型状态，便于用户反馈时对齐版本。
5. **文档收敛**：`docs/` 下已经有 15 份文档，状态分散在多处。建议新建 `docs/STATUS.md` 作为唯一的“当前状态”入口，其他文档只保留设计和证据；另外清理重复证据，例如 `desktop-app-startup-audit.json` 和 `desktop-app-startup-audit-20260927.json`、`render-report.json` 和 `render-report-isolated.json`，在 STATUS 中注明以哪一份为准。
6. **证据自动化**：本轮证据 JSON 大多是手工运行得到的。建议新建 `tools/run_acceptance.py`，一次运行测试、四类输出、基线比较、冻结 Worker 冒烟和哈希清单，输出到带日期的目录，这样每次发版前都能直接复现。
7. **模型目录体验**：模型是外部目录，首次使用时用户容易不知道放在哪里。建议在设置页显示期望的文件名和校验结果（SHA-256 是否匹配）。缺模型时，确认页给出明确提示：“模特图将使用保守构图，建议配置模型”。
8. **用户数据安全**：输出目录已有同名文件时，明确采用覆盖、跳过或重命名中的哪种策略，并在界面上说明。生成前检查磁盘剩余空间。
