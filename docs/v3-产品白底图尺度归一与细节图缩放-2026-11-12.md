## 1. 问题与证据

### 1.1 现象

鞋类白底图同组 19 张，主体框面积占画布 0.23–1.00，视觉重量差约 4 倍（用户截图红框 11 张偏大）。

### 1.2 根因（两类，分开处理）

| 编号 | 素材 | 走的代码 | 根因 |
|---|---|---|---|
| 06、07 | 不透明白底全貌图（正面 / 俯角，接近竖直） | `renderer.py:448` `_scaled_opaque_canvas`，缩放在 `:470-471` | `photo_scale = min(W*s/box_w, H*s/box_h)`：只约束"限制边"，竖长主体顶满高度 |
| 15、18 | 透明 PNG 全貌图 | `renderer.py:363` `_template_crop`（`:372` 的 `thumbnail` 与上式等价） | 同上，**另一个函数**，只改 `_scaled_opaque_canvas` 修不到这两张 |
| 08–14 | 半只鞋特写（原图中鞋已出画） | 分类 `v3_classification.py:184` 判 `detail` → `renderer.py:770-771` `_resize_cover` 铺满 | 细节图一律铺满，且 `engine.py:564-566` 把细节图的 `source_scale_adjustment` 强制归零，用户无法手动调小 |

全貌图输出面积可直接写成：

$$\text{面积} = s^2 \cdot \min(a,\ 1/a),\qquad a = \frac{\text{主体宽高比}}{\text{画布宽高比}}$$

侧面鞋 a≈2.7 → 0.26；正面鞋 a≈1.05 → 0.67。**差距完全来自摆放角度。** 模板 `s` 是按规范图（侧面鞋）校准的，所以只有规范角度是对的。

### 1.3 全品类实测（271 张：12 品类 + 鞋 4 色，1125×1500，全貌图之间面积最大/最小）

| 品类 | 现状 | 本方案后 | 改动张数 | 被否决的"固定上限 w≤0.72 h≤0.62"对规范图的影响 |
|---|---|---|---|---|
| 鞋（4 色） | 3.4× | 1.3× | 31/48 | 规范侧面图也缩小 14% |
| 帽子 | 1.6× | 1.0× | 7/7 | 缩小 5% |
| 护膝 | 1.4× | 1.1× | 4/6 | 不变 |
| 袜子 | 1.3× | 1.1× | 1/7 | 不变 |
| 马甲 | 1.3× | 1.3× | 0（1440 改 1 张） | 缩小 16% |
| 背心 / 长袖 / 长款羽绒服 | 1.0–1.2× | 不变 | 0 | 缩小 16–19% |
| 长裤 / 短裤 | 1.0× | 不变 | 0 | 长裤缩小 17% |
| 双肩包 / 软水壶 / 手套 | ~1.1× | 不变 | 0 | 软水壶缩小 17% |

素材与分析图：`~/Desktop/PixelFlow/05_测试素材与输出/构图分析-鞋白底-2026-11-12/`（`A_现状.jpg` / `B_半补偿γ0.5.jpg` / `C_等视觉重量γ1.jpg`、`各品类素材分布/`、`分析脚本/`）。测试素材：`05_测试素材与输出/各品类产品白底图/`、`~/Desktop/测试/测试鞋/`；规范图：`~/Desktop/测试/主图规范/`。

### 1.4 被否决的方案及原因

- **全局统一目标面积**：规范图本身各品类就不同（上衣 ≈0.54、鞋/帽/长裤 ≈0.24），统一会压小裤子、放大袜子。
- **固定双向上限（w≤0.72、h≤0.62）**：会改变几乎所有品类的规范图大小（见上表最后一列），即使只给鞋开，也压小标准侧面图。
- **γ=0.5 半补偿**：鞋差距仍 2.1×，未解决用户诉求。保留为配置项，作为回退手段。
- **细节图自动缩小**：12 个品类的细节图绝大多数是有意的满版特写（面料、logo、扣件），自动缩小会大面积误伤。

## 2. 第一阶段：全貌图尺度归一（核心）

### 2.1 算法

对每张走模板路径的全貌图，计算方向补偿系数 `m`，乘到现有缩放上：

```
canvas = W / H
fill(aspect) = min(aspect / canvas, canvas / aspect)
m = min(1.0, (fill(reference_aspect) / fill(box_w / box_h)) ** (strength / 2))
```

- `reference_aspect`：该品类规范图主体的宽高比（§2.3 表）。
- `strength`：即 γ，取值 [0, 1]，默认 `1.0`；`0` 等价于关闭。
- **上限 1.0**：只缩不放；主体宽高比等于规范时 `m == 1.0`，输出与现状完全一致。
- 系数与模板 `scale` 无关（`s` 在比值中约掉），对三个尺寸各自按画布比例计算。
- 与用户滑块 `source_scale_adjustment` **相乘叠加**（先 `m` 后滑块），用户仍可手动放大或缩小。

参考值（单测可直接断言，`reference_aspect=2.09`、`strength=1.0`）：

| 画布 | 主体宽高比 2.09 | 0.79（正面） | 0.58（竖立） | 3.0（更扁） |
|---|---|---|---|---|
| 1125×1500 / 1440×1920 | 1.0 | 0.6148 | 0.6812 | 1.0 |
| 1440×1440 | 1.0 | 0.7782 | 0.9083 | 1.0 |

### 2.2 配置：`worker/resources/templates/category_templates.json`

在**品类层级**（与 `sizes` / `scale` 同级）新增 `normalize` 对象。**不要放进 `sizes` 里**：旧引擎的 `legacy_engine/category_engine/category_template_manager.py:39-46` 会把 `sizes` 下每个键都当尺寸解析，遇到非尺寸字典会抛错；放在品类层级则会被它忽略（已核对 `:31-46`）。

```json
"shoes": {
  "sizes": { "...": "保持不变" },
  "normalize": { "enabled": true, "reference_aspect": 2.09, "strength": 1.0 }
}
```

| `knee_pads` | 1.12 | false | 用户确认后开 |

### 2.4 代码改动点（`worker/pixelflow_core/renderer.py`）

1. **新增配置读取**：仿照 `_template_config`（`:345-360`）新增 `@lru_cache` 函数，例如 `_template_normalization(resource_root, category) -> tuple[float, float] | None`。
   - 仅当 `normalize.enabled is True`、`reference_aspect > 0`、`0 <= strength <= 1` 时返回 `(reference_aspect, strength)`。
   - 字段缺失、类型错误或 JSON 异常一律返回 `None`（失败即保持现状，不得抛错中断渲染）。
2. **新增纯函数**：例如 `_orientation_factor(box_w, box_h, target, reference_aspect, strength) -> float`，实现 §2.1，单独可测。
3. **`_compose`（`:708` 起）**：在 `:736-746` 计算 `category_template` 的同一处，当 `enable_category_template` 且 `category_template is not None` 时取 `normalization`。**只有这两个条件都满足才启用**，所以模板选"无"时完全不受影响。
4. **`_scaled_opaque_canvas`（`:448`）**：增加可选参数 `normalization=None`。在 `:470` 算出 `photo_scale` 后、`:471` 乘 `scale_multiplier` 之前，乘以 `_orientation_factor(box_width, box_height, target, *normalization)`。调用点 `:813-822` 传入。
5. **`_template_crop`（`:363`）**：增加可选参数 `normalization=None`。用**加 1% 边距裁切后**的 `working.size` 计算系数，把 `thumbnail` 的目标框（`:372`）乘以 `m`。
   - **只在非透明主图调用点（`:798-804`）传入**；
   - 产品透明图调用点（`:749-755`，`transparent=True`）**不传**，透明图保持现状。
6. **不改动**：`_resize_cover`、`_resize_contain`、模特路径（`:772-796`）、贴边图走 cover 的分支（`:810-811`）、无模板时的 `_resize_contain`（`:805`）。
7. **`_compose_key`（`:828`）**：已包含 `layout.category`、`metadata.category`、`enable_category_template`，同一批次内无需新增键；配置文件变化不跨进程缓存，无需处理。
8. **VIP**：VIP 1440×1440 走同一个 `_compose` 主图分支，会自动生效，与 1440 主图保持一致（需在验收中目视确认）。
9. **可选（建议）**：把 `m` 写进 `RenderResult` 的 metadata 或诊断信息，例如 `orientation_scale`，方便复核页和诊断包排查。不做也不影响验收。

### 2.5 旧引擎兼容

- `legacy_engine/generate_main_images.py:1903` 把模板文件指纹写进 manifest，改 JSON 会让 v2.6 兼容路径的增量复用失效一次，属预期。
- 旧引擎不读 `normalize`，v2.6 对照输出不变（对照基线工具若比较 v3 与 v2.6，鞋类差异属预期，需在验收记录中注明）。

## 3. 第二阶段：细节图手动缩放（只缩不放）

第一阶段合入并经用户验收后再做。

### 3.1 行为

- 确认页细节图卡片显示"主体大小"滑块，范围 **-40% ~ 0%**（细节图不允许放大）；主图滑块保持 -50% ~ +50% 不变。
- 缩小时：
  - 判断原图四条边哪些是"被裁切边"：该边边框像素中，与背景色差 > 32 的占比 > 15%；
  - 被裁切的边在输出中**继续贴住画布对应边**；
  - 未裁切的方向空出的区域用背景补齐：取未裁切边的边缘色做 `_corner_gradient`，接缝参照 `_outer_background_blend_mask` 羽化；
  - **同一轴两侧都被裁切**（左右都贴边或上下都贴边）时，该轴不能缩到小于画布，`m` 被钳制；**四边都被裁切**的纹理特写，滑块实际无效果。
- 滑块为 0 时，必须与现状 `_resize_cover` **逐字节一致**。

### 3.2 改动点

| 位置 | 改动 |
|---|---|
| `engine.py:564-566` | `source_scale_adjustment` 对 `detail` 也透传（`model_detail` 仍为 0），并在 worker 侧钳到 `[-40, 0]` |
| `renderer.py:770-771` | `detail` 分支：调整量为 0 时保持 `_resize_cover`；否则走新的"贴边缩放"函数（建议独立函数 `_pinned_detail_shrink`） |
| `apps/desktop/src/App.vue:2523` | `.scale-option` 的 `hidden` 条件放开 `detail`；细节图的 `input range` 使用 `min="-40" max="0"`；"基础比例 / 最终比例"文案对细节图改为"缩小 x%" |
| 协议 | `source_scale_adjustments` 字段已存在（`workerProtocol.ts:109`），**无需改 schema** |

### 3.3 可选增强

分类阶段在 `metadata` 里写入 `cut_sides`（被裁切的边），前端据此对四边都贴边的图禁用滑块并提示"满版纹理特写不可缩小"。不做也可以，renderer 会钳制，只是用户拖动无反馈。

## 4. 测试要求（`worker/tests/test_renderer.py`）

第一阶段：

1. `_orientation_factor` 纯函数：断言 §2.1 参考值表（`assertAlmostEqual`，4 位小数）；`strength=0` → 1.0；结果永远 ≤ 1.0。
2. **规范角度零变化**：`shoes` + `enable_category_template`，源图主体宽高比 2.09 的白底图，开启归一与 `enabled=false` 两种配置输出**逐字节相同**。

4. **PNG 主图生效、透明图不生效**：RGBA 源图走主图路径时缩小；同一源图的透明输出与改动前一致。
5. **未启用品类不变**：`shirt`（`enabled=false`）竖长主体输出与改动前一致。
6. **配置异常回退**：`normalize` 缺字段、`strength` 越界、`reference_aspect<=0` 时，输出与无 `normalize` 一致，且不抛错。
7. **旧引擎仍能加载模板**：`CategoryTemplateManager(<真实 category_templates.json>)` 不抛错。

测试中需要临时修改配置时，用临时 `resource_root` 复制一份模板 JSON 再改，**不要改仓库内文件**；注意 `_template_config` / 新函数都带 `lru_cache`，测试间需 `cache_clear()`。

第二阶段：

8. 细节图调整量 0 → 与 `_resize_cover` 逐字节一致。

10. 四边贴边的细节图：任意调整量输出不变。

## 6. 风险与注意事项

1. **受保护品类**：`shirt`、`shoes`、`pants`/`long_pants` 的行为变化只允许发生在 `shoes` 的非规范角度上，且必须有回归证据（§4 第 2、5 条，§5.1 第 2 条）。
2. **两套"贴边"判断不一致**：分类器 `v3_classification.py:117-137`（128px、1.5% 边距）与渲染器 `_light_foreground_bbox` / `_light_foreground_touches_edge`（512px、边缘连通）标准不同。同一张图可能被分类为主图，却被渲染器当贴边图铺满。本次不统一，但第二阶段的"被裁切边"判断应**只在 renderer 内**做，不要再引入第三套标准。
3. **规则版本不升**：`v3-composition-11` 进入的是**模特模型结果缓存**的 identity（`model_cache.py`），产品白底渲染不读模型缓存。升版本会无谓地清掉模特缓存，还要四处同改。若执行方认为必须升，先回报。
4. **输出复用**：没有渲染版本号，旧图会被沿用。本次不改复用机制，只在验收和发布说明中强调"强制重跑"。如果日后要做，可把 `category_templates.json` 的指纹写进 v3 输出 manifest（旧引擎 `generate_main_images.py:1903` 已有同类做法）。
5. **只缩不放的副作用**：手套、袜子、护膝里有比规范**偏小**的全貌图（最小约为规范的一半），本方案不处理。是否允许适度放大由用户另行决定。
